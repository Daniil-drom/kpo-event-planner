# Следующие задачи

Подготовка каркаса не закрывает этап MVP. По таблице дисциплины срок MVP — 28 октября 2026 года. Порядок ниже позволяет собирать проверяемые функции постепенно.

## Работа с GitHub

Архив содержит изменения для ветки setup/project-foundation. Удалённый репозиторий не изменён. В нём нужно создать Issue на каркас, назначить исполнителя, добавить задачу в проект с колонками Todo / In Progress / In Review / Done, загрузить ветку и открыть связанный PR. В описание PR добавить Closes #<реальный номер Issue>. По формулировке задания задача должна быть Done до слияния в main.

Предлагаемый коммит: build: add application foundation and database migrations.

Для каждой следующей задачи используйте отдельные Issue, ветку и PR. Здесь перечислены заготовки задач, а не уже созданные Issues.

## 1. Импорт KudaGo и каталог

Реализовать клиент KudaGo на сервере, импорт городских мероприятий, мест, категорий и сеансов. Обработать пагинацию, таймауты и ошибки. Повторный импорт обновляет данные по внешнему ID и не создаёт дубликаты. Ошибка источника не стирает прежний каталог. В sync_runs записывается итог обновления.

Добавить API списка событий с фильтрами города, категории, даты и бесплатности, пагинацией и карточкой события. SQL-параметры передавать через JDBC, не склеивать пользовательский ввод со строкой запроса. Проверить неопределённые даты и часовые пояса. Ссылки на источник и использование материалов сверить с условиями KudaGo перед публикацией.

Готовность: реальные события одного города доступны через собственный API; повторная синхронизация не создаёт дубли; отказ источника обработан.

## 2. Регистрация и вход

Использовать Spring Security и стандартный PasswordEncoder, хранить только хеш пароля. Нормализовать email, обеспечить уникальность. Использовать сессионную cookie, защиту CSRF для изменяющих запросов и выход из системы. Настройки cookie учитывать отдельно для локального HTTP и публичного HTTPS.

Пользователя брать из серверной сессии, а не доверять userId из запроса. Не добавлять открытые методы изменения личных данных до настройки доступа.

Готовность: вход и выход работают; анонимный пользователь не может менять планы; пользователь не может читать или менять чужие планы.

## 3. Личный план

Реализовать создание, чтение, изменение и удаление посещений. Статусы: WANT_TO_VISIT, PLANNED, VISITED. Для PLANNED обязателен интервал, конец позже начала. При изменении обновлять updated_at. Проверять принадлежность записи пользователю на сервере.

Готовность: планы сохраняются после перезапуска; операции проверяют права и корректность дат.

## 4. Пересечения — основная бизнес-логика

Конфликт есть, если startA < endB и endA > startB. Проверять только PLANNED текущего пользователя; при редактировании исключать саму запись. Соседние интервалы не конфликтуют. При конфликте возвращать предупреждение, например HTTP 409 с конфликтующими посещениями; повторный подтверждённый запрос допускает сохранение с conflict_accepted.

Проверку и сохранение выполнять согласованно в транзакции; продумать параллельные изменения одного пользователя.

Готовность: модульные тесты покрывают соседние, частично пересекающиеся, вложенные и одинаковые интервалы, изменение своей записи, другой статус и другого пользователя.

## 5. Интерфейс

Подключить к собственному API каталог, карточку, фильтры, формы входа и личный план. Показывать состояния загрузки, пустого результата и ошибки. Внешний текст отображать безопасно, без вставки непроверенного HTML.

Готовность: пользователь проходит путь от выбора мероприятия до сохранения и изменения плана через браузер.

## 6. Проверки и завершение этапов

FoundationIT проверяет только каркас и ограничения БД. Он не заменяет интеграционный/E2E-тест ключевой пользовательской истории.

Добавить тест истории: зарегистрироваться → войти → выбрать событие → запланировать → получить предупреждение о конфликте → подтвердить → проверить сохранение. Добавить бизнес-тесты пересечений, доступа и ошибок импорта. Проверить Docker-скрипт на машине с Docker, CI — после загрузки ветки.

Провести нагрузочную проверку и сравнить измерения с целевыми задержками README; расчёт нагрузки не является измерением. Подготовить требуемый отчёт по дисциплине и демонстрацию. Заполнить корректные ФИО и группу.

## Где важно разобраться самостоятельно

Приоритет: путь HTTP-запроса через контроллер и сервис в БД; модель данных и транзакции; права доступа; алгоритм пересечений; обработка сбоев внешнего API; смысл написанных тестов. Для защиты нужно уметь объяснить эти решения и внести небольшое изменение самостоятельно.

Docker, CI, стили и шаблонную конфигурацию можно использовать как подготовленную основу. Карты, оплата, рекомендации, микросервисы и реальное развёртывание схемы масштабирования в текущий объём не добавлены.
